# 我用 LangGraph 复刻 Deep Research：一次多 Agent 系统的踩坑实录

> 项目：deep-research-agent —— 输入一个研究问题，Agent 团队自动完成「澄清 → 规划 → 并行检索 → 交叉验证 → 撰写报告」，产出带引用编号的 Markdown 研究报告。技术栈：LangGraph · DeepSeek/Ollama · Tavily · FastAPI(SSE) · Langfuse。
>
> 本文记录开发过程中真实踩到的三个坑，以及一套让"调优"变成"有数字可讲"的评测体系。

## 系统架构：五个角色 + 三件工程武器

整体是一个 LangGraph 状态机，五个节点各司其职：

```
coordinator(生成研究任务书) → [human-in-the-loop 审核]
  → planner(拆解子问题)
  → researcher × N(Send API 并行：搜索→抓取→摘要→反思循环)
  → verifier(交叉比对来源冲突)
  → writer(汇总为带引用编号的报告)
```

三件工程武器，每一个都直接对应生产环境的高频面试题：

- **并行 fan-out**：planner 通过 `Send API` 为每个子问题启动独立 researcher 实例。各实例上下文完全隔离（独立检索、独立笔记），只回传一条精炼笔记回主状态，`notes` 通道用 `operator.add` reducer 归并——避免长上下文互相污染，也天然规避并发写冲突。
- **human-in-the-loop**：coordinator 之后插入 `review_brief` 节点，用 LangGraph 的 `interrupt()` 暂停图执行，把研究任务书交给用户审核（网页端可以改写后继续）。恢复通过 `Command(resume=...)`，配合 SQLite checkpointer，**崩溃后还能 `--resume` 从断点精确续跑**——实测强杀进程后恢复时，输出的是"待执行节点：[researcher, researcher, researcher]"。
- **引用编号确定性生成**：报告的"参考来源"章节由代码按来源首次出现顺序去重编号，模型只负责在正文标 `[n]`。模型负责它擅长的（写作），编号这种确定性事务交给代码——这是抑制幻觉最便宜的手段之一。

## 坑一：思考 token 不计入 usage，却主导了延迟

评测冒烟时发现单题耗时 618 秒，但 usage 统计只有 5.1k 输出 token。按本地 4060 跑 qwen3:4b 的 62 tok/s 一算：605 秒 ≈ 3.7 万 token 的生成量。**差出来的 3.2 万 token 全是"思考"——它们不计入 `usage.completion_tokens`，但真实消耗墙钟时间。**

先试了 qwen3 官方的 `/no_think` 软开关（附加到提示词末尾）：无效。又试了 OpenAI 兼容接口层传参：Ollama 的兼容层不支持关思考。最后解法是绕开 OpenAI SDK，直接调 Ollama 原生 `/api/chat` 并传 `think: false`——单题延迟 618s → 258s，A/B 两批次统一走这条路径保证公平。

教训：**token 统计和延迟要对账**。当两者对不上时，先怀疑有"隐藏生成量"（思考、重试、草稿），而不是相信单一指标。

## 坑二：关掉思考通道后，推理泄露进了正文

`think:false` 之后冒烟，报告开头变成了这样：

> 首先，用户要求我撰写一篇结构化 Markdown 研究报告。报告的结构是：……

qwen3 关闭独立思考通道后，把推理过程直接写进了 `content`。更糟的是我当时用了 qwen3:4b 自己当 judge，**它给这份充满自言自语的"报告"打了忠实度 5 分**——同源模型既当运动员又当裁判，偏差远比想象中大。

最终解法分三层：

1. 换 **qwen2.5:7b-instruct**（无思考模式病理，指令遵循显著更好），输出 token 直接从 6217 降到 1943；
2. writer 节点加确定性兜底：输出若以非标题文本开头，从第一个 Markdown 标题行截断；
3. judge 提示词强调"只看论断与证据的对应关系"，并在评测报告里明确标注 judge 局限。

教训：**小模型当 judge 时，它连"输入是不是垃圾"都判断不了**。评测体系里最好安排一层确定性校验（正则、结构检查）兜住底线，LLM judge 只负责主观维度。

## 坑三：评测不是走过场，它真找到了缺陷

评测集 20 题（概念解释/技术对比/工具选型/技术趋势四类），每题跑完整研究流水线，五个指标：忠实度、覆盖度、引用质量（LLM judge 1~5 分）+ 引用有效性、来源利用率（正则确定性校验 0~1）+ token 用量与成本。

**全量 20 题**跑下来，baseline 暴露出一个真实的失败模式：**有 3 题（q01/q03/q19）的报告正文一个引用标记都没有**——writer 在 temperature 0.4 下的随机失败，16~23 个检索来源完全没被引用。对应的调优项是给 writer 加"严格 grounding 规则"：数字必须逐字来自研究笔记、每个论断必须挂 `[n]`、找不到引用的论断直接舍弃。同时把进入提示词的网页正文从 1200 提到 2000 字符、笔记长度提到 300~450 字。

同一评测集、同模型、同参数重跑（tuned 批次）：

| 指标 | baseline | tuned | Δ |
|---|---|---|---|
| 引用有效性（确定性） | 0.82 | **1.00** | **+0.18，失败案例清零** |
| 来源利用率（确定性） | 0.622 | **0.748** | **+20%** |
| 忠实度（LLM judge） | 4.8 | 4.8 | 持平 |
| 单题成本 | $0.004 | $0.005 | +$0.001 |
| 单题耗时 | 67.3s | 70.5s | +3.1s |

成本多了千分之一美元，换来引用失败率从 15%（3/20）清零到 0%——这就是"先把测量建起来，再谈调优"的意义：没有评测，我只会凭感觉说"提示词好像更好了"。

值得单独说的是：**评测工具本身也出过一次 bug**。第一版引用正则只匹配单个 `[n]`，而 tuned 在严格 grounding 下经常写成复合引用 `[2, 6, 12]`，正则匹配不到，导致 tuned 有两题被误判为"零引用"，指标被系统性低估（0.90 而非真实的 1.00）。修好正则、重算历史批次后数据才正确。教训很直接：**确定性指标看似可靠，但口径错了会直接误导调优方向，必须用边界用例自测**——这也是我后来给评测加了 `--recompute` 的原因：口径修正后不必重跑研究，直接重算派生指标。

## 诚实的局限

- judge 与被评对象同源（都是 qwen2.5:7b）。两组 LLM judge 主观分持平（4.8 vs 4.8），一部分原因是 7B judge 的分辨力不足以感知这种质量差异；对外绝对分数建议用更强的模型复评（例如 DeepSeek-V3）。
- 改进主要体现在确定性指标（引用有效性、来源利用率）上；主观质量维度没有可观测的退化，但也没有提升。
- 并行 researcher 在单机 Ollama 上受限于模型排队，换 API 服务后加速比才能接近线性。

## 写在最后

这个项目一开始的目标是"给简历加一个多 Agent 项目"，做完发现真正值钱的是评测体系：它把"我觉得变好了"变成"0.82 → 1.00"，还顺手抓出了评测工具自己的 bug。Agent 应用开发里，架构（LangGraph/并行/interrupt）决定下限，评测决定上限。

项目地址见仓库 README；完整 A/B 数据、逐题分数与报告原文在 `eval/results/` 目录。
